# Поставщики в уточнении, секции по типу, вечерняя пачка баннер/подряд

**Date:** 2026-08-24  
**Status:** Approved in chat  
**Repos:** TwentyView (доска, объект Поставщики, связь с позицией) и crmparserv2 (крон, Telegram, настройки часа и чата)  
**Related:** [reference directories phase 1](./2026-07-28-reference-directories-phase1-design.md), [taxonomy tipDetail](./2026-07-24-taxonomy-scoreboard-wave1-design.md). In crmparserv2: `2026-08-06-telegram-morning-digest-design.md`, `2026-08-07-telegram-digest-destination-ui-design.md`.

## Problem

1. Уточнение баннера и подряда — закрытый SELECT. Нового подрядчика (например «Саша Марда») нельзя ввести так, чтобы он появился у всех в том же списке.
2. Внутри сделки позиции разных типов перемешаны; нужно опционально резать их горизонтальными секциями (Реставрация / Плёнка / Баннера / Подряд / …) без смены порядка сделок.
3. На баннер и подряд нет вечернего текстового пинга в Telegram (бронь, позиция, «Фото в чат») накануне отгрузки, плюс догон если позицию завели уже вплотную к дате.

## Goals / non-goals

| In | Out |
|----|-----|
| Категория на Поставщике + связь позиция → поставщик | Мульти-категория на одной карточке |
| Комбобокс уточнения для Баннера и Подряд; ввод создаёт/реактивирует поставщика | Справочник «Выездной персонал» в этой ячейке |
| Скрытие = `isActive: false`; значения на позициях остаются | Физическое удаление карточки из UI доски |
| Личный тумблер секций по типу, default off, как «Умное» | Секции на мобильных карточках; плоско группировать всю таблицу |
| Вечерняя текстовая пачка 18:00 МСК, час в UI crmparser | Фото/альбомы, кнопки в Telegram, плёнка/реставрация в пачке |
| Догон в день отгрузки или после вечернего прогона | Напоминание за 5–7 дней |

## Decisions (locked)

| Topic | Choice |
|-------|--------|
| Список имён | Объект `supplier`, не расширение enum `tipDetail` |
| Категория | Один SELECT на карточку, значения как типы позиций |
| Кто видит нового | Весь workspace |
| Убрать из списка | Любой с доски → `isActive: false` |
| Уже выбранные после скрытия | Связь и имя остаются; в пикере неактивный виден только если это текущее значение |
| Дубль имени | Нормализация trim + регистр; та же категория → существующая карточка, при необходимости реактивация |
| `tipDetail` | Без изменений для Плёнка и Производство; для Баннера/Подряд больше не источник списка |
| «кто едет?» | Пустая связь с поставщиком |
| Секции | Внутри раскрытой сделки; порядок сделок и текущая сортировка позиций внутри секции сохраняются |
| Тумблер секций | `localStorage`, default выкл |
| Пачка | Одно текстовое сообщение; готовые входят, отмена нет |
| Время | 18:00 Europe/Moscow, час настраивается |
| Дата отгрузки | `opportunity.loadDate`, календарный день МСК |
| Чат | Отдельный ключ `telegram_chat_map`, не `okleyka.send` и не `digest.morning`; проверка в «Тест-Оклейка» |
| Транспорт | Bot API, как утренняя сводка |
| Идемпотентность | Не чаще одного успешного пинга на пару (позиция, дата отгрузки) |

## Architecture

```
TwentyView deals board
  tip BANNERA | PODRYAD → SupplierCombobox (filter category = tip)
    create/reactivate supplier + set relation
  tip PLENKA | PROIZVODSTVO | … → existing TipDetailSelect
  optional TypeSection rows inside expanded deal

crmparserv2
  cron (hour from settings, default 18 MSK)
    → loadDate = tomorrow
    → banner/podryad, stage ≠ OTMENA
    → one text message
  catch-up (board event and/or hourly sweep)
    → loadDate = today
      OR (loadDate = tomorrow AND now past today's send hour)
    → same text builder, skip if already logged for that loadDate
```

Generic RELATION cells on the board are read-only today (`isEditableFieldType`). Уточнение баннера/подряда — **отдельный редактор**, не generic relation cell.

## Data model

### Supplier: `category`

- App field via `yarn twenty dev:add field`
- Universal identifier: `3d719539-872e-4819-8bf3-462bbe7e69c3`
- Name: `category` · Label: `Категория` · SELECT, required for combobox rows
- Options (values = line-item `tip`):

| Value | Label |
|-------|--------|
| `BANNERA` | Баннера |
| `PODRYAD` | Подряд |
| `PLENKA` | Плёнка |
| `PROIZVODSTVO` | Производство |
| `RESTAVRACIYA` | Рест. плёнка |

v1 combobox uses only `BANNERA` and `PODRYAD`. Остальные значения — чтобы карточку можно было завести в справочнике заранее, без второго поля.

### Deal line item → supplier

- Source on `dealLineItem`: name `supplier`, MANY_TO_ONE, label `Поставщик`
- Universal identifier (source): `b6abc724-6526-4b39-8d1e-f9da6e58eff7`
- Inverse on `supplier`: ONE_TO_MANY, identifier `d686ae8a-d456-4652-8b42-50db8e02a609`
- Relation pair: `9033d2ae-59fc-4920-93d1-9cdad9d7f9c7`

Колонка доски по-прежнему называется **Уточнение**. Для баннера/подряда в ней имя поставщика; для остальных типов — `tipDetail`.

### `tipDetail`

Не удаляем поле. Зарплата оклейки и плёнка/производство продолжают его читать.

Для баннера/подряда после миграции источник правды — связь. Пока связь пустая, а `tipDetail` ещё `YURA` / `MAGA` / … — UI показывает историческую подпись и при первом сохранении с доски может проставить связь, если поставщик с таким именем уже есть.

Смена `tip`:

- На тип без комбобокса поставщика → очистить связь.
- Баннера ↔ подряд, категория выбранного поставщика не совпала с новым типом → очистить связь.
- Плёнка/производство: прежняя логика `nextTipDetailForTipChange`.

## Seed and migration

Один скрипт (local + явный prod-проход):

1. Создать активных поставщиков из текущих опций:

   - Баннера: Юра, Мага, Топильский (`YURA` / `MAGA` / `TOPILSKIY`). Не создавать «кто едет?».
   - Подряд: Глав принт, Паша виндер, Заря, Лиза сукно, Кувалдин клише, Своё.

2. Для позиций с `tip` баннер/подряд и известным `tipDetail` проставить связь на соответствующего поставщика. `KTO_EDET` и неизвестные значения — связь пустая, подпись не теряем в UI через fallback `getTipDetailLabel`.

Идемпотентность скрипта: поиск поставщика по нормализованному имени + категория.

## Board UI

### Supplier combobox

Показывать вместо `TipDetailSelect`, когда `tip` ∈ {`BANNERA`, `PODRYAD`}.

- Список: `isActive` и `category === tip`, плюс текущий выбранный даже если неактивен.
- Ввод нового имени + подтверждение: найти по нормализованному имени+категории; создать или `isActive: true`; записать связь.
- Пустое имя не создавать.
- «Убрать из списка» на пункте: `isActive: false` (не DELETE). Любой пользователь доски, у кого есть право обновлять поставщика.
- Нет права создавать/обновлять поставщиков: выбрать из уже загруженных можно; создать/скрыть — ошибка тостом.
- Сбой PATCH связи — тост, значение в ячейке откатить.

Плейсхолдер пустого списка: «введи имя».

### Type sections

Тумблер рядом с «Умное», подпись **«По типам»**, `role="switch"`, ключ `localStorage` вида `deals-board-type-sections` (не путать с expand-mode). Default: выкл. Нет `localStorage` → выкл, таблица как сейчас.

Только desktop `DealsTable`, только **внутри раскрытой сделки**. Порядок секций:

1. Реставрация (`RESTAVRACIYA`)
2. Плёнка (`PLENKA`)
3. Баннера (`BANNERA`)
4. Подряд (`PODRYAD`)
5. Производство (`PROIZVODSTVO`)
6. Не наше / без типа (`NE_NASHE` и `tip` пустой/неизвестный) — две подписи только если оба множества непусты; иначе одна полоска на фактическое множество. Если и `NE_NASHE`, и пустой тип есть — две секции: сначала «Не наше», затем «Без типа».

Пустая секция не рендерится. Полоска: `<tr>` + `colSpan`, стиль как дневной разделитель (тихий фон, `font.sizeXs`). Не кликается, не sticky. Порядок строк внутри секции — тот же, что у позиций этой сделки до группировки (стабильный `poryadok` / текущий child order).

Мобильный layout: тумблер можно показать, но группировка v1 не применяется.

## Telegram evening digest

### Settings (crmparser UI, вкладка/страница Telegram)

| Key | Meaning |
|-----|---------|
| `telegram_chat_map['banner_podryad.evening']` | `{ chatId, threadId? }`, тот же нормализатор, что у `digest.morning` |
| `telegram_banner_podryad_hour` | Целое 0–23, default **18**, таймзона `Europe/Moscow` |

Кнопки: сохранить назначение, тест в чат (короткая строка «Тест пачки баннер/подряд»). Нет чата — ошибка в UI, крон не шлёт и пишет лог.

### Evening run

- Расписание: каждый день в настроенный час МСК (как digest cron: `node-cron` + TZ).
- Вселенная: неотменённые сделки с `loadDate` = завтра (MSK day key).
- Позиции: `tip` ∈ {`BANNERA`, `PODRYAD`}, `stage !== OTMENA` (**Готово входит**).
- Одно `sendMessage` на прогон. Нет позиций — сообщение не слать (тишина, не «пусто»).
- Успех → строка в SQLite send-log на каждую включённую позицию: `lineItemId`, `loadDate`, `channel=banner_podryad.evening`. Повтор того же вечера / повторный крон не дублирует уже залогированные id.
- Twenty недоступен → прогон не пишет успех; следующий крон или hourly sweep повторит.

### Catch-up

Срабатывает, если позиция баннер/подряд, не отмена, ещё нет лога на её `loadDate`, и:

- `loadDate` = сегодня, или
- `loadDate` = завтра **и** текущее МСК-время уже после часа вечерней отправки.

Триггеры:

1. После создания/смены `tip` на баннер/подряд с доски — POST в crmparser (тот же секрет, что telegram events), чтобы догон был сразу.
2. Hourly sweep в crmparser — позиции из парсера и пропущенные события.

Несколько догонов за короткое окно можно склеить в одно сообщение (debounce ~30–60 с на процессе). Формат тот же, заголовок «Догон · отгрузка DD.MM».

Один ретрай сети; после неудачи позиция без лога успеха.

### Message shape (text only)

```
Накануне отгрузки DD.MM

Бронь: {booking или —}
• {имя позиции}
  Фото в чат

Бронь: …
```

- Бронь: `extractBookingId(opportunity.name)` как в оклейке; пусто → «—».
- Группировка блоков по брони (сделки с одной бронёй рядом).
- Файлы не прикладывать.

### Bot

Тот же Bot API token, что для `digest.morning` (не user-bot оклейки). Staging проверять в «Тест-Оклейка».

## Error handling

| Case | Behavior |
|------|----------|
| Пустое имя в комбобоксе | Не создавать поставщика |
| Дубль имени+категории | Переиспользовать / реактивировать |
| Нет прав на supplier | Тост; связь не врём |
| PATCH связи упал | Тост + rollback ячейки |
| Нет localStorage | Секции выкл |
| Нет chat map | Крон skip + ошибка в настройках |
| Twenty down на кроне | Нет success-log |
| Догон network fail | 1 retry, потом лог ошибки |

## Testing

**Unit (TwentyView):** нормализация имени; фильтр поставщиков по категории и `isActive`; смена tip очищает чужую связь; порядок секций и скрытие пустых; стабильный порядок внутри секции.

**Unit (crmparser):** day-key завтра/сегодня; окно catch-up относительно часа; фильтр tip/stage; идемпотентность лога; сборка текста пачки; merge settings hour + chat map не затирает `okleyka.send` / `digest.morning`.

**Manual:** localhost доска — ввод «Саша Марда», второй раз в списке у другого пользователя/инкогнито после sync; скрыть — позиция живая; тумблер «По типам». crmparser — тест в «Тест-Оклейка», смена часа.

## Implementation notes

- Новые сущности: `yarn twenty dev:add field` (категория, связь); UUID v4 выше — канон для app-owned ids.
- После front/logic: `yarn twenty apply` и hard refresh.
- Не коммитить токены и chat_id.

## Out of scope

- Мульти-категория одного поставщика
- Секции на мобиле и плоская таблица «все реставрации всех сделок»
- Фото в вечерней пачке
- Напоминалки для плёнки/реставрации
- Удаление enum-опций `YURA` из metadata в этом же релизе (можно позже, когда миграция на prod подтверждена)
