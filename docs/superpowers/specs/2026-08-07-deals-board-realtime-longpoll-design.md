# Realtime борда «Реализация» через хаб событий и long-poll

Дата: 2026-08-07

## Задача

Изменения, сделанные одним пользователем борда (стадия сделки, стадия позиции, комментарии,
любые поля видимых сущностей), должны появляться у остальных пользователей за 1–2 секунды,
без F5.

## Почему SSE не подходит

Front-component исполняется в Web Worker с opaque origin (`blob:null`), поэтому хост
подменяет `fetch` компонента на мост через `postMessage`. Мост в бандле хоста
(`FrontComponentRenderer`) буферизует ответ целиком:

```js
d4 = async (response) => {
  if (Number(response.headers.get("content-length") ?? 0) > 52428800) throw tooLarge();
  let body = await response.text();            // ждёт закрытия потока
  ...
  return { status, statusText, headers, body }; // строка через postMessage
}
```

Хост выполняет запрос сам (с `credentials: "omit"`) и ждёт `response.text()`. Для
`text/event-stream` этот промис не разрешается, пока поток открыт, поэтому внутри воркера
`fetch` никогда не возвращает `Response`: `graphql-sse` не получает ни `connected`, ни `next`,
ни одного сообщения. В мосте нет ни `ReadableStream`, ни обработки `text/event-stream` —
стриминг там не поддержан архитектурно. Подписки на события хоста в bridge API тоже нет
(доступны только `navigate`, `requestAccessTokenRefresh`, снекбары и подобное).

Серверная часть при этом полностью исправна. Проверено живым экспериментом из Node с тем же
application-токеном и с теми же `operationSignature`, что шлёт борд: после `addQuery`
в поток пришли `CREATED`, `UPDATED` (`updatedFields: ["name"]`) и `DESTROYED` за 150–500 мс.
Отдельно выяснилось, что Twenty не публикует событие, если обновление не меняет значение
(запись того же имени события не даёт) — именно это маскировало результат первой пробы.

Вывод: внутри компонента работают только запросы, которые **завершаются**. Значит транспорт —
long-poll.

## Архитектура

```
Twenty core (публикация события)
      │  SSE (внутренний адрес, минуя Traefik)
      ▼
crmparserv2: потребитель потока ──► журнал событий с курсором (в памяти)
                                          │
                                          ▼
                        GET /api/twenty/events?since=&epoch=  (long-poll до 25 с)
                                          ▲
                        logic function /deals-board/events (прокси)
                                          ▲
                        клиент борда: цикл long-poll ──► applyObjectRecordEvent
```

Разделение ответственности:

- **Потребитель потока** знает только про Twenty SSE и про то, как положить событие в журнал.
- **Журнал** знает только про хранение и выдачу по `since`; про Twenty ничего не знает.
- **Long-poll-эндпоинт** — тонкий слой над журналом.
- **Logic function** — чистый прокси по образцу `line-item-list-status-batch`, без своей логики.
- **Клиентский хук** ничего не знает о происхождении событий и переиспользует существующий
  слой применения (`applyObjectRecordEvent`, `resolve-event-patch`) без изменений.

## Хаб в crmparserv2

### Журнал

- Кольцевой буфер в памяти. Запись: `{ seq, receivedAt, event }`, где `event` сохраняет
  исходную форму Twenty вместе с `properties` (`updatedFields`, `diff`, `after`).
- `properties` сохраняются намеренно: из них клиент патчит кеши точечно. Без них каждое чужое
  изменение приводило бы к полному перезапросу тяжёлых списков борда.
- Ограничения: не более 2000 записей и не более 8 МБ суммарно, что закончится раньше;
  старые записи вытесняются.
- `seq` монотонно растёт в пределах эпохи.

### Курсор и эпоха

- При старте сервиса генерируется `epoch` (UUID v4).
- Ответ всегда: `{ epoch, cursor, events, reset? }`.
- Клиент присылает `since` и `epoch`.
- `reset: true` возвращается, когда эпоха не совпала (хаб перезапустился) или `since` старше
  начала буфера (клиент отстал, события вытеснены). Клиент один раз инвалидирует все ключи
  реестра и продолжает с возвращённого курсора.
- Первый опрос без курсора получает актуальный `cursor` и пустой список событий: борд к этому
  моменту уже загрузил свежие данные, сброс не нужен.

### Long-poll

- Есть события новее `since` — ответ сразу.
- Иначе запрос висит до 25 секунд и возвращается пустым с тем же курсором (heartbeat), после
  чего клиент опрашивает снова.
- Каждый открытый борд держит один запрос в Express и одно выполнение logic function.

### Жизненный цикл потока

- Потребитель запускается при старте сервиса: создаёт `eventStreamId`, открывает SSE по
  внутреннему адресу (`TWENTY_API_URL`, `http://twenty-server:3000`), затем регистрирует
  `addQuery` по каждому наблюдаемому объекту.
- Watchdog: если 60 секунд нет ни событий, ни keepalive-двоеточий (Twenty присылает их
  примерно раз в 10 секунд), поток считается мёртвым.
- Переподключение с бэкоффом от 0.5 до 5 секунд, с новым `eventStreamId` и повторной
  регистрацией запросов.
- События, опубликованные во время обрыва, теряются, поэтому после каждого переподключения
  в журнал дописывается служебная запись `RESYNC`; клиенты, увидев её, инвалидируют всё.

### Ограничения, зафиксированные явно

- Журнал живёт в памяти, поэтому crmparserv2 работает в одном экземпляре. При нескольких
  репликах клиенты прыгали бы между эпохами и постоянно ресетились. Сейчас единственный
  экземпляр и так подразумевается: сервис использует локальный sqlite.
- Журнал общий на воркспейс, без фильтрации по правам: любой аутентифицированный пользователь
  борда получает все события наблюдаемых объектов. Для этого борда это те же данные, которые
  он и так видит, но, в отличие от родного SSE Twenty, фильтрации по ролям здесь нет.

### Риск, снимаемый первым шагом

У crmparserv2 в окружении лежит `TWENTY_API_TOKEN` — это API-ключ, а эксперимент проводился на
application-токене. Первый шаг реализации — спайк: открыть `onEventSubscription` этим ключом,
зарегистрировать `addQuery` и убедиться, что события приходят. Если API-ключу подписка
недоступна, вход хаба меняется на вебхуки Twenty: они дают те же изменения с ретраями, но в
другом формате payload, который приводится к форме `ObjectRecordEvent` на входе журнала.
Остальная архитектура при этом не меняется.

## Приложение Twenty

### Logic function

`src/logic-functions/deals-board-events.ts`, новый UUID v4:

- путь `/deals-board/events`, метод GET, `isAuthRequired: true`, `timeoutSeconds: 60`;
- читает `since` и `epoch`, проксирует в `/twenty/events` через `crmparserProxyFetch` (базовый
  адрес прокси уже включает `/api`, поэтому итоговый путь — `/api/twenty/events`);
- отдаёт ответ как есть через `jsonProxyResponse`.

### Клиентский хук

`useDealsBoardEventsSync` вместо `useDealsBoardRealtimeSync`:

- один запрос в полёте, следующий стартует сразу после ответа;
- отмена через `AbortController` при размонтировании;
- события применяются по порядку через `applyObjectRecordEvent`, курсор двигается;
- при `reset: true` или записи `RESYNC` один раз инвалидируются все ключи реестра;
- на ошибках бэкофф из нынешнего `sse-reconnect` (переименованного в модуль бэкоффа): 1 секунда
  с удвоением и потолком 30 секунд;
- в отличие от текущего SSE-хука, цикл **не останавливается навсегда** после пяти неудач подряд:
  для long-poll это означало бы, что деплой crmparser или короткий сетевой сбой убивает realtime
  до перезагрузки страницы. Вместо остановки — бесконечные повторы с потолком бэкоффа и запись в
  лог только на первой неудаче в серии, чтобы не спамить консоль;
- оптимизации по видимости вкладки нет: компонент живёт в воркере, где нет `document`, поэтому
  скрытая вкладка продолжает опрашивать. Это одно висящее соединение, цена приемлема.

### Реестр объектов

Соответствие «объект → ключи react-query» выносится из `invalidateObjectQueries` в отдельный
модуль, которым пользуются и применение событий, и путь сброса:

| Объект | Ключи запросов |
| --- | --- |
| `opportunity` | `opportunities`, `deals-board-page` |
| `dealLineItem` | `lineItems`, `deals-board-page` |
| `okleykaDealShare` | `okleyka-shares`, `okleyka-salary` |
| `okleykaSalaryEntry` | `okleyka-salary-entries`, `okleyka-salary`, `okleyka-salary-history` |
| `company` | `companyNames` |
| `restorationTemplate` | `restorationTemplatesCatalog` |

Имена объектов сверены с метаданными воркспейса (`okleykaDealShare`, `okleykaSalaryEntry`,
`restorationTemplate`), ключи — с кодом борда. `fieldStaff` в реестр не входит: борд его не
читает.

Такой же список наблюдаемых объектов нужен хабу и остаётся отдельной константой на стороне
crmparser. Эти два списка должны совпадать; расхождение означает, что события объекта
доходят, но никуда не применяются, либо наоборот.

### Что удаляется

- `src/deals-board/realtime/useDealsBoardRealtimeSync.ts`
- `src/deals-board/realtime/event-stream-api.ts`
- `src/deals-board/realtime/on-event-subscription.ts`
- их тесты, а также костыли последних дней: таймерные кики регистрации и кеш токена сессии.

Остаются `apply-object-record-event.ts`, `resolve-event-patch.ts`, `types.ts`.

### Выключатель

Переменная окружения `TWENTY_EVENTS_ENABLED=false` на crmparserv2: эндпоинт начинает отвечать
`200 { "disabled": true }`, и клиент после такого ответа перестаёт опрашивать до перезагрузки
страницы. Если в проде что-то пойдёт не так, realtime гасится настройкой, а не откатом релиза.

Выключатель именно на стороне хаба, а не в `application-config.ts`: инъекция переменных приложения
в песочницу фронт-компонента не проверена, а env-конфиг парсера — проверенный путь. Дополнительный
плюс в том, что гасится сам источник нагрузки, включая висящие long-poll запросы.

## Обработка ошибок

| Ситуация | Поведение |
| --- | --- |
| crmparser не настроен | функция отвечает 503, клиент пишет в лог один раз и продолжает повторы с потолком бэкоффа |
| хаб перезапущен | смена эпохи → `reset: true` → полная инвалидация у клиента |
| клиент отстал, события вытеснены | `reset: true` → полная инвалидация |
| обрыв SSE у хаба | переподключение с бэкоффом, запись `RESYNC` в журнал |
| поток жив, но данных нет 60 с | watchdog пересоздаёт поток |
| ошибка сети у клиента | бэкофф от 1 с с удвоением, потолок 30 с, повторы без остановки |

## Проверка

На стороне crmparser:

- юнит-тесты журнала: нумерация `seq`, вытеснение по количеству и по объёму, `reset` при
  отставшем курсоре и при смене эпохи;
- разрешения long-poll: мгновенный ответ при наличии событий, ожидание, пустой heartbeat;
- переподключение потребителя с вставкой `RESYNC` (на подменённом fetch/потоке).

В приложении:

- тест logic function по образцу тестов существующих прокси;
- тесты хука на фейковых таймерах: порядок применения событий, движение курсора, сброс при
  смене эпохи, бэкофф на ошибках, отсутствие параллельных опросов.

Сквозная проверка: скрипт создаёт и меняет запись в Twenty, второй открытый борд должен
показать изменение за пару секунд — тем же способом, которым доказана работоспособность
серверной части.

## Порядок выкладки

1. Спайк с `TWENTY_API_TOKEN` (подписка API-ключом).
2. Деплой crmparserv2 с хабом: он бездействует, пока его не опрашивают.
3. Деплой приложения: logic function, реестр, хук, удаление SSE-слоя.
4. Проверка в двух браузерах на проде, при проблемах — выключатель.
